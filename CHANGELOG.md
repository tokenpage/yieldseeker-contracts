# Changelog

## Unreleased

### Wallet and factory

- `AWKAgentWalletFactory` and `YieldSeekerAgentWalletFactory` store configuration by agent profile. `setAdapterRegistry`, `setFeeTracker` and `setSwapPolicy` configure the profile; `adapterRegistry`, `feeTracker` and `swapPolicy` read it. `RegistryUpdated`, `FeeTrackerUpdated` and `SwapPolicyUpdated` replace the unprofiled `TrackerUpdated` event. A wallet stores its profile at initialization and copies the registry, tracker and policy at sync. `createAgentWallet(owner, index, baseAsset, agentProfile, feePlans)` sets its plans per fee type. V3 uses a new factory; the V2 factory remains live.
- `AWKAgentWalletV3` and `YieldSeekerAgentWalletV3` replace V2 behavior while retaining the V1 storage namespace. `AgentWalletStorageV3` appends `agentProfile`; `YieldSeekerStorageV1` appends `swapPolicy`. Owners can withdraw any token the tracker accounts for. Before ERC20 withdrawals, modules get a gas-limited, failure-tolerant `TRANSFER_OUT` report, then a successful fixed withdrawal sends exactly the requested amount. `withdrawableBalance` accounts for base-asset fees owed. `collectFees()` is removed; fees are paid as actions occur. `AWKSelfManagedAgentWalletV3` has no factory: the owner sets its registry and operators, chooses upgrades and may upgrade to an implementation of their choice. V1 and V2 wallets on the V2 factory remain unchanged.
- The V1 wallet sources and V2 storage facade were removed. `YieldSeekerStorageV1` and the V1 errors are in the V3 files. `IAWKAgentWalletFactory` no longer exposes parameterless `adapterRegistry()`.
- Wallet signature validation uses `ECDSA.tryRecover`; malformed signatures return `SIG_VALIDATION_FAILED` instead of reverting, allowing ERC-4337 dummy-signature gas estimation. Owner UserOperations also accept ERC-1271 approval from a contract owner. ECDSA is checked first, so EIP-7702 EOAs still use ECDSA. Operator signatures remain ECDSA-only and authorize adapter execution only, and only in a UserOperation with a paymaster, so a compromised operator can't spend the wallet's ETH or EntryPoint deposits on gas. Adapter calls never fall through to ERC-1271, so validating one, even with a dummy signature, reads only the wallet's own storage (ERC-7562); contract owners call `executeViaAdapter` directly. Storage tags claiming ERC-7201 were removed; wallet slots remain plain `keccak256(namespace)` hashes.
- Wallets also accept `PackedUserOperation`s from the canonical v0.7, v0.8 and v0.9 EntryPoints through a second `validateUserOp(PackedUserOperation, bytes32, uint256)`, alongside the v0.6 EntryPoint. Both validators share `_validateUserOpSignature(signature, callData, paymasterAndData, userOpHash)` and the `_validateNonce` hook, and `isEntryPoint(address)` replaces the single EntryPoint check in `onlyOwner` and `onlyExecutors`. `test/fork/PackedEntryPointsFork.t.sol` runs paymaster-sponsored operator single and batch adapter calls, self-paid owner withdrawals and a real Safe owner's withdrawal through each of the v0.7, v0.8 and v0.9 EntryPoints on Base, and checks that unsponsored operator calls, stranger signatures, operator-signed owner calls, a signature for another EntryPoint and a replayed UserOperation fail.
- `upgradeToLatest()` calls `upgradeToAndCall(implementation, syncFromFactory())`, so the new implementation syncs during the upgrade. Previously the old implementation's sync ran after the implementation switch.
- `YieldSeekerAgentWalletV3` rejects the inherited three-argument `initialize(owner, index, profile)` with `NotAllowed`; YieldSeeker wallets require a base asset. `withdrawAssetsToUser` and `withdrawAllAssetsToUser` let owners withdraw several accounted tokens in one call. The per-token logic uses `_withdrawAssetToUser` and `_withdrawAllAssetToUser` hooks overridden by the YieldSeeker wallet; AWK token withdrawals are `nonReentrant`.
- The owner-withdrawal fee-settlement test checks gas limits from 60,000 to 3,000,000; each withdrawal either reverts or settles the full fee.

### Fees

- `YieldSeekerFeeTracker` moved to `src/fees/` and was rewritten around modules. It stores one module per fee type, ABI-encoded plans, wallet plans, the wallet factory and fee collector. `setFeeModule` checks `FEE_TRACKER` and `FEE_TYPE`; a replacement must accept every existing plan and can add plans. The timelock admin controls modules, plans, factory and collector. The plan-manager role and vault accounting interface are gone.
- Only the wallet factory sets a wallet's plans at creation. Plans are module-defined, validated by `isValidPlan`, numbered from 0 per fee type and never change. A wallet uses plan 0 for an unlisted fee type. Tracker views call modules with a gas limit; a failed module counts as accounting for nothing and owing nothing, and the base asset is always accounted for. The caller must leave sufficient gas for the module checks.
- Adapters report `DEPOSIT`, `WITHDRAW`, `SWAP`, `REWARD_SALE`, `CLAIM`, `DEBT_CHANGE` and `TRANSFER_OUT` action IDs and structs from `FeeActions`; wallets report `TRANSFER_OUT` before owner withdrawals. The tracker passes each action to all modules in insertion order. Each module pays from the base asset left by prior modules, and the adapter sends the total to the collector in one transfer. A new fee type needs a module. A new action needs an ID and struct; modules ignore unknown actions.
- `YieldSeekerYieldFeeModule` (`YIELD_FEE`) tracks only cost basis per target. A withdrawal releases basis in proportion to the position share withdrawn, including rebasing vaults and lending collateral; output above released basis is yield. Base-asset claims and base asset from `REWARD_SALE` are yield. Other `SWAP` actions are not. Fees use the wallet's plan and round up. Per-token reward accounting, share tracking, double-charge guards and exchange-rate conversion were removed.
- `YieldSeekerBorrowFeeModule` (`BORROW_FEE`) charges yearly on each market's debt, including interest, under its registry target. It accrues on debt at the previous report, converts through the lending market's price and pays from the base asset when one is available. If a report has no price, such as after an external repayment, it uses the market's last reported price. Borrowed tokens can be withdrawn in full. The module stores market last prices, `tokenDebt` per borrowed token across markets, and borrowed-token accounting. Fee accrual and base-asset conversion round up.

### Adapters

- A V3 vault registry and vault, reward and swap adapters were added. V2 vault wallets keep the V2 registry and adapters. Both vault registries must contain the same targets. Swap adapters are shared with the V3 borrow registry.
- AWK lending adapters were added for Aave V3, Aave V4 and Morpho Blue. Each market is a registry target derived by `marketTarget(market)` from its encoded market data and requires a timelocked registration. `checkpoint(market)` moves no funds and reads debt. Lending adapters read the protocol's own oracle price and the wallet's collateral. YieldSeeker lending adapters require collateral equal to the wallet's base asset, report debt changes and checkpoints, and account for supplied and withdrawn collateral as a yield-fee position keyed by `marketTarget(market)`. Aave V3 requires a 3.3 or newer pool and supports only eMode 0.
- Aave V3 supplies enable collateral on every supply. `withdrawCollateral` at or above the collateral balance withdraws the full balance. The Aave V4 spoke returns shares and assets; its adapter reports the returned asset amount. A zero market price (a zero Morpho oracle price, or a zero Aave collateral or debt price) is reported as zero instead of dividing by it: a borrow then reverts with `ZeroDebtPrice`, and other lending actions go ahead with the borrow fee module using the market's last price. A market oracle that reverts still makes the action revert.
- Compound V2 and Moonwell withdrawals redeem cToken amounts, not underlying amounts. The backend must send cToken amounts (`assets × 1e18 / exchangeRateCurrent`) or the full cToken balance. V2 wallets keep their V2 adapter. `AWKCompoundV2Adapter` wraps underlying paid as native ETH back into the underlying token.
- Compound V3 withdrawals are capped at the wallet's Comet balance, preventing a withdrawal from borrowing against collateral supplied to that wallet's account. Its approval resets after `supply`, since Comet treats `type(uint256).max` as a request to supply the borrow balance. A deposit that credits no Comet balance reverts. The yield module treats base asset received from a position with no recorded basis as yield.
- Vault adapters measure deposited and withdrawn amounts from balances. ERC-4626 and Aave V3 withdrawals report base asset actually received, not protocol return values. Withdrawal share is measured from the change in wallet vault-token balance, including shares, cTokens, rebasing aTokens and Comet balances. Vault `Deposited` and `Withdrawn` events are emitted by `execute`. An ERC-4626 redemption that pays nothing reverts, so a queued redemption (yoUSD and yoEUR queue redemptions above their free balance) can't be recorded as a withdrawal of zero that releases cost basis; `test/fork/AsyncVaultFork.t.sol` covers yoUSD.
- The V3 Merkl adapter's call is `claim(tokens, amounts, proofs)`. It builds one `users` entry per token, all set to the wallet. The backend uses the three-argument call for V3; V2 wallets retain the four-argument V2 call. The Moonwell reward adapter reports WELL and base-asset rewards; base-asset rewards are charged when claimed.
- Every adapter except the agent-transfer adapter follows `execute` input decoding and validation, an operation layer with YieldSeeker rules and fee reports, then the AWK protocol call. The four vault adapters share the vault operation layer; vault, swap and lending operation layers are shared by their concrete adapters. Swap before/after hooks and `SwapBalanceSnapshot` were removed.

### Swaps and oracle

- Swap rules moved to one factory policy per agent profile, copied by wallets at sync. Shared Uniswap V3 and Aerodrome V2/CL adapters use router targets and report the action returned by the profile policy. A base-asset sale must leave no fees owed or it reverts with `FeesOwed`.
- `YieldSeekerVaultSwapPolicy` allows sellable reward tokens to be sold for the base asset. `YieldSeekerBorrowSwapPolicy` also allows base asset to be swapped into a borrowed token, at most `MAX_SLIPPAGE_BPS` below the oracle. Borrowed tokens cannot be sold. `REWARD_SALE` charges the yield fee on reward sales, not other swaps. `SwapAboveDebt` reverts if the wallet would hold more of a borrowed token than its last reported debt (`tokenDebt`). The cap is on the balance held, not the total bought, since agent transfers can move the token to the owner's other wallets.
- Swap policies reject tokens mapped as registry targets regardless of the sell list. `allowSellingAllTokens` must remain disabled. A replacement borrow fee module must import `tokenDebt` because the borrow policy reads it.
- `YieldSeekerPriceOracle` uses Chainlink feeds, per-asset staleness limits and an L2 sequencer uptime check. It is used only for the borrow policy's floor on base-asset sales. `SetPriceSource.s.sol` rejects feeds whose `aggregator()` is zero; use a raw feed because a protocol wrapper can cap answers or rewrite timestamps. The oracle rejects zero and future timestamps. The borrow swap floor rounds up; its oracle quote rounds down.
- Aerodrome Slipstream has three CL routers. `Deploy.s.sol` deploys one CL adapter per router and registers each in both V3 registries. The adapter has no tick-spacing allowlist, so the tokenized-stock pools (third factory, spacing 10) are reachable; `test/fork/SwapFork.t.sol` swaps through the third router at spacing 10.
- A collateral-to-debt cycle can still lose up to 1% per hop.

### Transfers

- `YieldSeekerAgentTransferAdapter` transfers accounted tokens between wallets of the same owner and factory. It is registered as its own target, so the owner does not need to act. Both trackers must account for the token. `TRANSFER_OUT` settles fees before the exact amount moves.

### Scripts and operations

- `Deploy.s.sol` deploys V3 contracts and schedules one timelock batch for factory profile wiring, two fee trackers and their modules, registries, adapters and known targets. The vault tracker has `vaultYieldFeeModule`; the borrow tracker has `borrowYieldFeeModule` and `borrowFeeModule`. It copies V2 vault targets to matching V3 adapters and configures the borrow registry's routers, Merkl and agent transfers. `RegisterVault.s.sol` registers a vault in both vault registries. `RegisterBorrowMarket.s.sol` validates and registers a market; `SetPriceSource.s.sol` checks and schedules a feed. V2 addresses remain under `agentWalletV2*` keys in `deployments.json`. Existing users move to new wallets by withdrawing to the new wallet address.
- `Deploy.s.sol` schedules `setFeeCollector` when a tracker differs from `FEE_COLLECTOR_ADDRESS`. It grants `SERVER_ADDRESS` if missing but never removes an operator. It refuses to replace a registry, tracker or fee module already in use. Registry unpause remains timelocked.
- `RegisterBorrowMarket.s.sol` requires canonical market bytes. `RegisterVault.s.sol`, `AddSellableTokens.s.sol` and the `Deploy.s.sol` configuration batch salt their timelock operations with the block number, so the same operations can be scheduled again later. `Deploy.s.sol` redeploys the borrow swap policy when `MAX_SLIPPAGE_BPS` changes. `dry-run-deploy.sh` prints the forge output when a run fails.
- `Deploy.s.sol` creates the V3 factory with the Safe as admin, emergency admin and operator. The factory address, and so every wallet address, depends only on the Safe and the factory bytecode; the Safe can be recreated at the same address on other chains, so `(owner, index)` gets the same wallet address on every chain without depending on a deployer key. The Safe then hands the admin role to the chain's timelock, the operator role to `SERVER_ADDRESS` and the emergency role to the deployer in one transaction; `script/factory-handover.sh` lists the calls and refuses a timelock with no code, `check-timelock.sh` bundles them ahead of the timelock batch after checking that `DEPLOYER_ADDRESS` is the vault registry's emergency admin, and `dry-run-deploy.sh` executes them and checks the factory address and final roles. `deployCreate2` reuses a contract already deployed at its CREATE2 address with the same init code.
- Operator revocation uses the factory's `emergencyAdmin` and `EMERGENCY_ROLE`; `removeAgentOperator(operator)` is immediate, while adding an operator stays with the admin. Anyone can call input-free `syncFromFactory()` so the platform can sync every wallet. Registry pause and target or adapter removal are emergency operations; unpause is timelocked.

### Toolchain

- Solidity `0.8.28` → `0.8.38`, OpenZeppelin Contracts and Contracts Upgradeable `5.5.0` → `5.7.0`, forge-std `1.12.0` → `1.17.0`. CI pins Foundry `v1.9.0` instead of nightly.
- OpenZeppelin `5.6` makes `ERC1967Proxy` revert when created without init data. `AWKAgentWalletProxy` overrides `_unsafeAllowUninitialized()` to keep its fixed creation code, so wallet addresses still depend only on `(owner, ownerAgentIndex)`; the factory initializes the wallet in the same transaction.
- The storage libraries' `layout()` is renamed `getLayout()` because `layout` is becoming a keyword. Virtual modifiers and contract-type comparisons, deprecated in Solidity `0.8.31`, were removed.
- `foundry.toml` turns off compiler metadata (`bytecode_hash = "none"`, `cbor_metadata = false`) so bytecode, and with it the factory address, depends on code rather than file contents. `foundry.lock` matches the pinned libraries and `make install` installs Foundry `v1.9.0`.

## Agent wallet V2

- Added `AWKAgentWalletV2` and `YieldSeekerAgentWalletV2` with EntryPoint-relayed owner actions.
- Blocklist management, ERC20 and ETH withdrawals, synchronization and UUPS upgrades can be paymaster-relayed; owner signatures remain required.
- Operator signatures are limited to adapter execution.
- Added `AgentWalletStorageV2` as an explicit facade over the unchanged V1 storage layout.
- Existing V1 wallets retain their state when upgraded; V1 implementation behavior remains unchanged.
